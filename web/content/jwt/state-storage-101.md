> 本文是「登录状态与踢下线·0 基础」系列第 1 章。读这一篇不需要任何后端经验，我们从一个生活问题讲起：**网站是怎么记住"你是你"的？**

## 1. 一个根本性的尴尬：HTTP 是个金鱼

你打开网站，登录成功；刷新一下页面，居然还认识你。这看似天经地义，其实背后藏着一个大难题——

**HTTP 协议本身是"无状态"的。** 意思是：浏览器每发一次请求，对服务器来说都是**陌生人第一次敲门**。它不记得你 3 秒前刚登录过。

打个比方：你去游泳馆，存包、进闸机、再出来上厕所、再进闸机——如果闸机不认手环，每次都要你重新买票。手环就是网站用来"记住你"的凭证。网站领域的"手环"有三代：

| 代际 | 方案 | 一句话原理 |
|---|---|---|
| 第一代 | Cookie | 服务器把信息直接写在你的浏览器里 |
| 第二代 | Session | 服务器自己记账本，你只领一个编号 |
| 第三代 | Token (JWT) | 服务器给你一张防伪签名卡片，信息写在卡上 |

## 2. 第一代：Cookie——把外套寄存在你自己身上

最早的思路简单粗暴：登录成功后，服务器把"你是谁"直接塞给你的浏览器（一个叫 `Cookie` 的小文本），下次请求自动带上。

```http
Set-Cookie: user=yuxm; role=user
```

问题显而易见：**信息在用户手里**。浏览器 F12 一看，改个 `role=admin` 再发回去？服务器就信了。相当于把写着"我是老板"的胸牌自己画——谁都能画。
## 3. 第二代：Session——服务器自己记账本

于是演进到 Session：用户信息只存在**服务器**手里，浏览器只领一个不透明的小编号（Session ID）：

```http
Set-Cookie: session_id=a8f3k9  （一个随机编号，看不出任何信息）
```

服务器端有一本账：

```
a8f3k9 -> { user_id: 1, role: user, login_at: ... }
```

浏览器伪造编号没用——编了账本上查不到，等于游客。**这套方案好用了很多年，直到「集群」出现。**

### 集群时代的 Session 之痛

单机时代，账本就放本机内存，天经地义。但一旦为了扛流量/做高可用部署了 **2 台服务器 + 负载均衡**，尴尬来了：

```
请求1 -> 服务器A（登录，账本写在A的内存里）
请求2 -> 负载均衡 -> 服务器B（查账本：查无此人 -> 请重新登录？!）
```

你在 A 登录，下一个请求被分到 B，B 的内存里根本没有你的记录——**每刷新一次都可能被登出**，体验灾难。

初代解法是"会话黏连"（Session Sticky）：负载均衡记住你，把你永远发往 A。但这等于把负载均衡的高可用性废了一半：A 一宕机，A 上的所有用户全部掉线，且黏连表本身也是新的单点。

**于是人们想通了一件事：账本不该放在"任何一台业务服务器"里，它应该独立出来。**

## 4. 第三代的共同前提：状态独立存储

不管是 Session 集群方案还是 JWT，绕不开同一个动作——**把"登录状态"从业务服务器的内存里拿出来，放到一个所有机器都能访问、且它自己很可靠的地方**。这个"中央保管箱"在工程上几乎总是选 Redis：

- 所有业务服务器共用一份状态 -> 负载均衡打到哪台都认账
- Redis 独立部署 -> 业务服务器随便增减、随便重启，登录态不丢
- 天然支持过期时间 -> 登录态自动失效

本站就是这么做的。生产配置（`deploy/docker-compose.yml`）里，Redis 是一个独立容器，API 容器自己**一个字节都不存用户状态**，所有"这个 token 还有效吗"的判断都去问 Redis：

```yaml
services:
  redis:            # 中央保管箱：黑名单、版本号、限流计数全在这
    image: redis:7
  api:              # 业务服务器：无状态，想扩几个副本扩几个
    depends_on: [redis]
```

这就是标题里说的「**状态怎么独立存储的**」——一句话：**业务机器无状态，状态集中在 Redis，业务机器可以随生随灭，Redis 独立保障可靠。**
## 5. 那 JWT 又是干什么的？它和 Redis 保管箱矛盾吗？

这里有一个流传很广的误解，值得掰清楚。

JWT（JSON Web Token）的本质是**一张防伪签名的卡片**：

```
用户信息.签名   <-  签名由服务器用密钥计算，伪造信息 = 签名对不上 = 立刻识破
```

它的招牌卖点是"无状态认证"：服务器**不用查任何账本**，验一下卡片上的签名就知道你是谁——听起来好像不需要 Redis 了？

**但只要产品有"踢人下线"这个需求，纯无状态的 JWT 就露馅了**：卡片有效期内无法作废。想象几个真实场景：

- 管理员要踢掉一个恶意用户
- 用户点了「退出所有设备」
- 账号被盗，用户改密码想让旧登录全部失效

这些场景里，**卡片还在用户手里，签名也是真的**——纯无状态 JWT 对此完全无解。解法是让 Redis 继续当保管箱：卡片签名用来"免查库验明正身"，Redis 用来"记录这张卡是否被吊销"。

两代方案在本站是**组合使用**的，这正好是第 2 章的主题：黑名单 + 版本号双保险，全部落在 Redis 这一个保管箱上。

## 6. 小结：三个演进，一条主线

```
Cookie       ->  信息在用户手里（不安全）
Session      ->  信息在单机内存（集群下裂开）
独立状态层   ->  Redis 中央保管箱 + 轻便凭证（JWT）
   主线：状态离"业务机器"越来越远，业务机器越来越"轻"，扩容越来越随意
```
