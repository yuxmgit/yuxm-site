> 「Redis 可靠性与集群实录」系列第 1 章。先抛一个扎心的问题：Redis 的数据放内存里，服务器断电不就没了吗？——对，不加任何措施就是这样。可靠性不是开关，是**一层一层叠出来的**。

## 1. 第一层：持久化——解决"断电丢数据"

Redis 默认把数据放内存，快是快了，但内存是易失的（断电即蒸发）。持久化就是"把内存数据抄一份到硬盘"，有两种抄法：

### RDB：定时拍快照

每隔一段时间，把整个内存**拍一张照片**存成紧凑的二进制文件。

- 优点：文件小、恢复快，像游戏存档
- 缺点：**两次快照之间的数据，宕机就没了**。每 5 分钟拍一次，最多可能丢 5 分钟

### AOF：记操作流水账

每一条写命令（SET/DEL...）都追加记录到一个日志文件。重启时把流水账重放一遍，数据就回来了。

- 优点：最多丢 1 秒（`appendfsync everysec` 档位）
- 缺点：日志越积越大、恢复比 RDB 慢，像游戏操作录像

本站所有 Redis 节点（包括演示集群的 6 个节点）都开了 `appendonly yes`，即 AOF。生产上常见 **RDB + AOF 双开**：AOF 保证丢得少，RDB 保证恢复快。

**但这只解决了"硬盘坏了"——机器整个没了呢？** 单机持久化救不了单机灾难。于是有了第二层。

## 2. 第二层：主从复制——数据多机备份

再找一台机器，让它当"影子"，实时把主节点的数据抄一份：

```
主节点 (写) ──实时同步──> 从节点 (备份/分担读)
```

- 平时：读写分离，主写从读，主的压力小一半
- 灾难时：主挂了，从节点手里有一份（几乎）完整的数据

**注意一个容易被忽略的真相：主从复制是异步的。** 主节点写完自己的内存就回复客户端了，同步给从节点是"顺手的事"。主节点刚写完、还没来得及同步就断电的那几百毫秒数据，从节点也没有——这叫复制窗口，工程上是用"丢一点"换"整体可用"。

**还有个新问题：主挂了，谁来宣布主挂了、谁来指挥从节点上位？** 总不能半夜人肉爬起来敲命令吧。于是有了第三层。

## 3. 第三层：哨兵（Sentinel）——自动换主的指挥官

哨兵是几个独立的小进程，啥数据都不存，专职干三件事：

1. **盯**：每秒 ping 主节点，超时没响应就判定"主观下线"
2. **商量**：多台哨兵（通常 3 台）投票，多数认定"真的挂了"（客观下线）才行动——防止单个哨兵网络抖动误判
3. **换**：从节点里挑一个提升为新主，其他从节点改跟新主，客户端被引导连新主

这就是传说中的**故障自动转移**。整个换主过程通常 10 秒级，无需人工介入。

## 4. 第四层：Cluster——把"分片"和"高可用"合体

哨兵解决了"主挂了怎么办"，但没解决另一个问题：**数据太多，一台内存装不下怎么办？**

Redis Cluster 的答案是"分家"：把 16384 个哈希槽（slot）切成若干份，每份交给一个主节点管。

```
3 主 3 从：
主7001 管 slot 0-5460        主7002 管 slot 5461-10922       主7003 管 slot 10923-16383
  └ 从7006                     └ 从7004                        └ 从7005
```

- **写入路由**：key 经 CRC16 算出槽号，自动找到负责的主节点（客户端 `-c` 参数自动跟随重定向）
- **高可用**：每个主都有从，主挂了它的从自动上位（这本质上把哨兵机制内置进了集群）
- **扩容**：数据多了就加节点，槽可以在线迁移

**一句话总结四层阶梯：**

```
单机内存（快但易失）
  └+ RDB/AOF        解决断电
      └+ 主从复制   解决单机灾难
          └+ 哨兵   解决"谁指挥切换"
              └+ Cluster  解决"一台装不下" + 内置故障转移
```

## 5. 回到本站：登录状态为什么敢放 Redis？

本站的 JWT 黑名单、版本号、限流计数全在 Redis 里——如果 Redis 数据全丢，后果是：所有用户被登出（版本号回源 DB 后可恢复）、限流计数清零。**丢得起，且能自愈**（见 [JWT 踢下线一章的"回源"设计](/posts/jwt/state-kick-offline-101)），所以生产单节点 Redis + AOF 就够用。
